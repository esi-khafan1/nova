# Nova | نووا

نووا یک پلتفرم فارسی مشاوره تحصیلی و برنامه‌ریزی مطالعه برای دانش‌آموزان پایه دهم تا دوازدهم است. رابط کاربری کاملاً RTL است و نسخه عمومی روی Vercel منتشر می‌شود.

- Production: https://nova-six-steel.vercel.app/
- Repository: https://github.com/esi-khafan1/nova
- شاخه اصلی: `main`
- شاخه طراحی فعال در زمان نگارش: `feature/warm-no-gray-landing`
- Pull Request طراحی: https://github.com/esi-khafan1/nova/pull/5

## وضعیت فعلی محصول

موارد زیر در پروژه پیاده‌سازی شده‌اند:

- لندینگ‌پیج فارسی و واکنش‌گرا
- ثبت‌نام، ورود و خروج با Supabase Auth
- مدیریت نشست سمت سرور با `@supabase/ssr`
- جدول پروفایل‌ها با نقش‌های `student`، `counselor` و `admin`
- انتقال خودکار کاربر به داشبورد متناسب با نقش
- داشبورد دانش‌آموز و ویرایش نام، شماره تماس و پایه تحصیلی
- ثبت رشته تحصیلی دانش‌آموز
- انتخاب مستقیم دانش‌آموز توسط مشاور
- برنامه‌ریز هفتگی مشاور با ساعت، مدت، درس، فصل، نوع فعالیت و توضیحات
- ذخیره برنامه به‌صورت پیش‌نویس یا انتشار برای دانش‌آموز
- نمایش برنامه هفتگی منتشرشده در داشبورد دانش‌آموز
- فهرست آماده دروس و فصل‌های کنکور بر اساس رشته و پایه
- داشبورد مشاور
- داشبورد مدیر و مدیریت نقش کاربران
- محافظت از مسیرها و کنترل دسترسی بر اساس نقش

بخش‌هایی مانند جلسات مشاوره، منابع، پرداخت و اعلان‌ها هنوز باید به‌صورت کامل توسعه داده شوند.

## فناوری‌ها

- Next.js 15 App Router
- React 19 و TypeScript
- Supabase Auth و PostgreSQL
- Supabase SSR
- Vercel
- ESLint
- فونت فارسی از بسته‌های `@fontsource-variable`

## اصول ثابت طراحی

این قواعد در **تمام صفحات سایت** شامل لندینگ، Auth، داشبوردها، منوها، فرم‌ها و حالت‌های مختلف رابط کاربری الزامی‌اند:

- از رنگ خاکستری در هیچ بخش رابط کاربری استفاده نشود؛ شامل پس‌زمینه، متن، Border، Icon، Shadow، Overlay، Placeholder، حالت Disabled و Hover.
- خاکستری‌های موجود یا رنگ‌های نزدیک به خاکستری باید با رنگ‌های زنده و هماهنگ برند جایگزین شوند.
- رنگ‌های خنثی مجاز: سفید گرم، کرم، شیری و هلویی بسیار روشن.
- رنگ‌های متن و کنتراست: سرمه‌ای عمیق یا قهوه‌ای گرم؛ از مشکی خالص نیز استفاده نشود.
- نارنجی رنگ Accent برند است و برای CTA، وضعیت فعال، پیشرفت و جزئیات کلیدی استفاده می‌شود؛ نباید تمام صفحه را اشباع کند.
- برای سطوح تیره از سرمه‌ای استفاده شود، نه مشکی یا خاکستری.
- حذف خاکستری نباید باعث کاهش خوانایی شود؛ همه ترکیب‌های رنگی باید کنتراست دسترس‌پذیر داشته باشند.
- قبل از تحویل هر تغییر UI، صفحات دسکتاپ و موبایل و همچنین حالت‌های Hover، Focus، Disabled و فرم‌ها از نظر نبود رنگ خاکستری بررسی شوند.

## اجرای محلی

پیش‌نیازها:

- Node.js 20 یا جدیدتر
- npm
- دسترسی به پروژه Supabase نووا

راه‌اندازی:

```bash
git clone https://github.com/esi-khafan1/nova.git
cd nova
npm install
cp .env.example .env.local
npm run dev
```

سپس سایت را در `http://localhost:3000` باز کنید.

### متغیرهای محیطی

```env
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=your-publishable-key
```

کد فعلی برای سازگاری، `NEXT_PUBLIC_SUPABASE_ANON_KEY` را نیز به‌عنوان جایگزین کلید publishable می‌پذیرد.

مقادیر واقعی را فقط در `.env.local`، تنظیمات Vercel یا ابزار امن مدیریت Secrets قرار دهید. هیچ کلید خصوصی، `service_role`، رمز عبور یا توکن دسترسی را داخل Git، README یا چت قرار ندهید.

## وابستگی‌های مورد انتظار در Supabase

کد فعلی انتظار دارد این موارد در پروژه Supabase موجود باشند:

- Supabase Auth با ورود ایمیل و رمز عبور
- جدول `profiles`
- ستون‌های `id`، `full_name`، `role`، `grade`، `study_field`، `phone` و `created_at`
- نقش‌های `student`، `counselor` و `admin`
- تابع RPC با نام `admin_set_user_role`
- جدول‌های `counselor_students`، `weekly_plans` و `weekly_plan_items`
- تابع‌های RPC با نام‌های `counselor_student_directory`، `counselor_select_student` و `save_weekly_plan`
- RLS و Policyهای مناسب برای مشاهده و ویرایش پروفایل‌ها

قبل از تغییر Schema، Migration یا Policyها ابتدا وضعیت فعلی پروژه Supabase بررسی شود. تغییرات دیتابیس بدون تأیید و بدون برنامه بازگشت انجام نشوند.

- نبودن هم‌پوشانی و بریدگی محتوا

- عملکرد مسیرهای ورود و داشبورد

## گردش کار Git و انتشار

1. آخرین نسخه `main` را دریافت کنید.
2. برای هر قابلیت یا اصلاح، یک شاخه جدید از `main` بسازید؛ مانند:
   - `feature/...`
   - `fix/...`
   - `chore/...`
3. تغییرات فقط روی همان شاخه Push شوند.
4. Vercel برای شاخه، Preview Deployment می‌سازد.
5. بعد از **هر Push**، Agent باید منتظر بماند تا Deployment در Vercel به وضعیت نهایی `Ready/Success` یا `Failed` برسد؛ قبل از آن نباید کار را تکمیل‌شده اعلام کند.
6. پس از موفقیت Deployment، Agent باید لینک دقیق همان Preview را در پاسخ برای صاحب پروژه ارسال کند. اگر Deployment ناموفق بود، ابتدا Build Log بررسی و خطا برطرف شود.
7. Preview در دسکتاپ و موبایل بررسی و ایرادات برطرف شوند.
8. پس از موفقیت `lint` و `build`، Pull Request به `main` ساخته شود.
9. ادغام با `main` فقط بعد از تأیید صریح صاحب پروژه انجام شود.
10. `main` نسخه Production است؛ تغییر آزمایشی مستقیماً روی آن Push نشود.

استثنا: تغییر صرفاً مستنداتی مثل README، در صورت درخواست صریح صاحب پروژه، می‌تواند مستقیم روی `main` انجام شود.

## راه‌اندازی سریع یک سشن جدید با AI

برای اینکه در یک سشن جدید نیازی به توضیح دوباره پروژه نباشد، اتصال‌های زیر را آماده کنید.

### 1. GitHub

اتصال رسمی GitHub/MCP را فعال کنید و به repository زیر دسترسی خواندن و نوشتن بدهید:

```text
esi-khafan1/nova
```

دسترسی موردنیاز:

- خواندن فایل‌ها و تاریخچه Commitها
- ساخت Branch
- Push فایل و Commit
- ساخت و به‌روزرسانی Pull Request
- خواندن وضعیت Branch و PR

در ابتدای سشن از AI بخواهید ابتدا `README.md`، آخرین `main`، Branch فعال و PRهای باز را بخواند. دسترسی حذف Repository یا مدیریت تنظیمات سازمان لازم نیست.

### 2. Supabase

اتصال رسمی Supabase را فعال کنید و پروژه‌ای با نام `nova` را در اختیار سشن قرار دهید.

برای عیب‌یابی کامل، اتصال باید امکان موارد زیر را بدهد:

- مشاهده Schema، Tableها، Functionها و Policyها
- اجرای Queryهای فقط‌خواندنی برای بررسی داده
- مشاهده Auth و خطاهای مرتبط، در حدی که اتصال رسمی ارائه می‌کند
- مشاهده Logهای دیتابیس و API
- اجرای Migration فقط هنگام درخواست و پس از تأیید

از ارسال دستی رمز، access token، کلید `service_role` یا اطلاعات ورود در چت خودداری کنید.

### 3. مرورگر اشتراکی و Vercel

در ابتدای هر سشن، **دسترسی استفاده از مرورگر اشتراکی برای Agent باید فعال باشد**. صرفاً متصل بودن GitHub/MCP یا Supabase کافی نیست؛ Agent برای باز کردن داشبورد Vercel، بررسی Deployment، مشاهده Build Log و تست Preview به دسترسی مرورگر نیاز دارد.

پس از فعال شدن مرورگر، Agent باید صفحه ورود Vercel را باز کند، گزینه **Continue with GitHub** را بزند و با همان حساب GitHub متصل به Vercel وارد شود. نام کاربری، رمز عبور و کد تأیید باید فقط از ورودی امن مرورگر وارد شوند و هرگز در چت، Commit یا Log قرار نگیرند. بعد از ورود، پروژه `nova` و Preview مربوط به Branch فعال باز و بررسی شود. این فرایند همان ورود مرورگری Vercel از طریق حساب GitHub مالک Repository است و با اتصال Vercel/MCP تفاوت دارد.

مراحل الزامی شروع سشن:

1. دسترسی مرورگر اشتراکی را فعال کن.
2. `https://vercel.com/login` را در مرورگر باز کن.
3. **Continue with GitHub** را انتخاب کن.
4. ورود GitHub و کد تأیید را فقط از ورودی امن مرورگر دریافت کن.
5. پس از ورود، پروژه `nova`، Deployment مربوط به Branch فعال و لینک دقیق Preview را پیدا کن.

موارد موردنیاز:

- مشاهده Production و Preview Deploymentها
- مشاهده Build Log و Runtime Log
- مشاهده وضعیت Environment Variableها بدون افشای مقدار Secretها
- Redeploy در صورت نیاز

برای این پروژه، مسیر پیش‌فرض دسترسی Vercel همان ورود مرورگری با GitHub است. اتصال Vercel/MCP اختیاری است و جایگزین فعال‌سازی مرورگر و بررسی واقعی Preview نمی‌شود.

### 4. پیام پیشنهادی شروع سشن

پس از برقرار شدن اتصال‌ها، این پیام برای شروع سریع کافی است:

```text
روی پروژه Nova در repository `esi-khafan1/nova` کار کن. ابتدا README، آخرین main، Branchهای فعال و PRهای باز را بررسی کن. دسترسی مرورگر اشتراکی را فعال کن و برای دسترسی به Vercel از صفحه Login گزینه Continue with GitHub را بزن؛ اطلاعات ورود و کد تأیید را فقط از ورودی امن مرورگر دریافت کن. پروژه nova و Preview مربوط به Branch فعال را باز کن. برای تغییرات کد از main یک Branch جدید بساز. بعد از هر Push منتظر تکمیل Deployment Vercel بمان، نتیجه را بررسی کن و لینک دقیق Preview را برای من بفرست. بدون تأیید من Merge نکن. برای دیتابیس و Auth فقط از اتصال رسمی Supabase استفاده کن. اگر باگ گزارش کردم، ابتدا Logهای Vercel و Supabase را بررسی کن و بعد کمترین اصلاح امن را انجام بده.
```

اگر قرار است کار قبلی ادامه پیدا کند، نام Branch یا لینک PR را نیز در همان پیام بنویسید.

## قواعد ایمنی برای Agent

- قبل از ویرایش، وضعیت Branch و آخرین Commit بررسی شود.
- تغییرات محلی یا کار ناتمام دیگران بدون اجازه حذف یا بازنویسی نشود.
- برای هر کار کدنویسی از Branch مجزا استفاده شود.
- هیچ Secret یا اطلاعات شخصی در خروجی، Log، Commit یا PR قرار نگیرد.
- تغییرات دیتابیس ابتدا بررسی و سپس با Migration قابل بازگشت انجام شوند.
- برای رفع باگ، ابتدا شواهد از Logها جمع‌آوری و سپس کوچک‌ترین اصلاح ممکن اعمال شود.
- بعد از هر Push، تکمیل Deployment Vercel بررسی و لینک دقیق Preview گزارش شود.
- قبل از Merge، Preview و Build نهایی بررسی شوند.
- Merge و انتشار عمومی فقط با تأیید صاحب پروژه انجام شود.
