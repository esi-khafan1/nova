# Nova | نووا

نووا یک پلتفرم فارسی مشاوره تحصیلی و برنامه‌ریزی مطالعه برای دانش‌آموزان پایه دهم تا دوازدهم است. رابط کاربری کاملاً RTL است و نسخه عمومی روی Cloudflare Workers منتشر می‌شود.

- Production: https://nova-academy.ir/
- Repository: https://github.com/esi-khafan1/nova
- شاخه اصلی: `main`
- شاخه طراحی فعال در زمان نگارش: `feature/warm-no-gray-landing`
- Pull Request طراحی: https://github.com/esi-khafan1/nova/pull/5

## وضعیت فعلی محصول

موارد زیر در پروژه پیاده‌سازی شده‌اند:

- لندینگ‌پیج فارسی و واکنش‌گرا
- ثبت‌نام، ورود و خروج با Supabase Auth
- مدیریت نشست سمت سرور با `@supabase/ssr`
- جدول پروفایل‌ها با نقش‌های `student`، `counselor` و `admin`
- انتقال خودکار کاربر به داشبورد متناسب با نقش
- داشبورد دانش‌آموز و ویرایش نام، شماره تماس و پایه تحصیلی
- ثبت رشته تحصیلی دانش‌آموز
- انتخاب مستقیم دانش‌آموز توسط مشاور
- برنامه‌ریز هفتگی مشاور با ساعت، مدت، درس، فصل، نوع فعالیت و توضیحات
- ذخیره برنامه به‌صورت پیش‌نویس یا انتشار برای دانش‌آموز
- نمایش برنامه هفتگی منتشرشده در داشبورد دانش‌آموز
- ثبت انجام هر فعالیت توسط دانش‌آموز
- گزارش پیشرفت هفتگی، ماهانه و کلی با تفکیک زمان، درس و فصل
- فهرست آماده دروس و فصل‌های کنکور بر اساس رشته و پایه
- داشبورد مشاور
- داشبورد مدیر و مدیریت نقش کاربران
- محافظت از مسیرها و کنترل دسترسی بر اساس نقش

بخش‌هایی مانند جلسات مشاوره، منابع، پرداخت و اعلان‌ها هنوز باید به‌صورت کامل توسعه داده شوند.

## اصول ثابت طراحی

این قواعد در **تمام صفحات سایت** شامل لندینگ، Auth، داشبوردها، منوها، فرم‌ها و حالت‌های مختلف رابط کاربری الزامی‌اند:

- از رنگ خاکستری در هیچ بخش رابط کاربری استفاده نشود؛ شامل پس‌زمینه، متن، Border، Icon، Shadow، Overlay، Placeholder، حالت Disabled و Hover.
- خاکستری‌های موجود یا رنگ‌های نزدیک به خاکستری باید با رنگ‌های زنده و هماهنگ برند جایگزین شوند.
- رنگ‌های خنثی مجاز: سفید گرم، کرم، شیری و هلویی بسیار روشن.
- رنگ‌های متن و کنتراست: سرمه‌ای عمیق یا قهوه‌ای گرم؛ از مشکی خالص نیز استفاده نشود.
- نارنجی رنگ Accent برند است و برای CTA، وضعیت فعال، پیشرفت و جزئیات کلیدی استفاده می‌شود؛ نباید تمام صفحه را اشباع کند.
- برای سطوح تیره از سرمه‌ای استفاده شود، نه مشکی یا خاکستری.
- حذف خاکستری نباید باعث کاهش خوانایی شود؛ همه ترکیب‌های رنگی باید کنتراست دسترس‌پذیر داشته باشند.
- قبل از تحویل هر تغییر UI، صفحات دسکتاپ و موبایل و همچنین حالت‌های Hover، Focus، Disabled و فرم‌ها از نظر نبود رنگ خاکستری بررسی شوند.

## اجرای محلی

### قواعد تأییدشدهٔ گوشی — برای توسعه‌دهندگان و AIهای بعدی

این موارد خواستهٔ صاحب پروژه‌اند و فقط در عرض‌های گوشی (`max-width: 700px`) اعمال می‌شوند. استایل‌های لندینگ در `app/landing-mobile.css`، پس از سایر استایل‌های لندینگ بارگذاری می‌شوند. تغییر این قواعد، حذف کنترل‌ها یا تعمیم آن‌ها به دسکتاپ بدون درخواست صریح مجاز نیست.

- بخش مسیر تحصیلی (دهم، یازدهم، دوازدهم، نتیجه): دو ستون، دو ردیف؛ هر چهار مورد و ترتیبشان حفظ شود.
- مزیت‌های «چرا نووا»: دو ستون، سه ردیف؛ هر شش عنوان، آیکن و متن حفظ شود.
- پیش‌نمایش مجله، پادکست و خبر در **لندینگ گوشی**: حداکثر دو کارت تازه، کنار هم در یک ردیف. توضیح کوتاه هر کارت نمایش داده نشود؛ عنوان، تصویر، اطلاعات انتشار و لینک باقی بمانند. تاریخ سمت راست و «بخوان / شنیدن پادکست / متن خبر» سمت چپ همان ردیف قرار بگیرند، نه زیر تاریخ. در عرض باریک، متن درون ستون خودش بشکند، نه اینکه روی ستون دیگر بیفتد. لینک «همه» حفظ شود. این محدودیت نباید به صفحات آرشیو یا جزئیات، کوئری دیتابیس، یا دسکتاپ منتقل شود.
- یوتیوب و تلگرام در یک ردیف دو‌تایی؛ لینک‌ها و توضیحات باقی بمانند و متن درون کارت باریک نشکند یا از آن خارج نشود.
- فوتر گوشی: لوگو و جملهٔ معرفی تکراری نمایش داده نشوند، اما **لوگوی navbar و همهٔ لینک‌های فوتر** حفظ شوند. فقط دو ستون و دو عنوان «نووا» و «خدمات» باشد؛ عنوان «قوانین و ارتباط» در گوشی نمایش داده نشود. تماس با ما و حریم خصوصی زیر نووا؛ شرایط استفاده و بازگشت وجه زیر خدمات باشند. همهٔ ۱۳ مقصد حفظ شوند، زیر هم و بدون گروه سوم. ساختار دسکتاپ تغییر نکند.
- تصویر اصلی لندینگ در گوشی و دسکتاپ همان تصویر ارسالیِ ستاره کنار برنامهٔ مطالعه و نمودار پیشرفت (`public/nova/hero-panorama.svg`) باشد. متن و CTAهای گوشی روی تصویر قرار بگیرند، نه در بلوکی جدا از تصویر؛ در گوشی از تصویر عمودی `hero-mobile.svg` استفاده شود؛ هیچ لایهٔ سفید، گرادیان پوشاننده، blur یا کاهش opacity روی عکس مجاز نیست. تصویر قدیمی برای حفظ سابقه حذف نشود.
- ورود و ثبت‌نام گوشی: دکمهٔ نمایش/پنهان‌سازی رمز در سمت راست، جای قفل باشد؛ قفل تکراری نمایش داده نشود. متن ایمیل، رمز و placeholder رمز از چپ آغاز شود؛ دکمهٔ چشم حداقل ۴۴×۴۴ و با صفحه‌کلید قابل استفاده بماند.
- عنوان بالای فرم در گوشی کامل باشد: «یک شروع روشن، به سبک خودت». دکمهٔ بازگشت در گوشی «بازگشت» و در دسکتاپ «بازگشت به خانه» باشد؛ هیچ‌کدام حذف نشوند.
- تغییرات مشابهِ آینده در همین بخش‌ها با این قواعد هماهنگ باشند، نه بهانه‌ای برای تغییر خودسرانهٔ بخش‌های دیگر. پیش از تحویل، عرض‌های ۳۲۰، ۳۶۰، ۳۹۰ و ۴۳۰ پیکسل، حالت‌های ورود/ثبت‌نام و نمایش رمز، و نیز حفظ ظاهر دسکتاپ بررسی شوند. اسکرول افقی، هم‌پوشانی، بریدگی متن یا فونت ریزتر از ۱۴ پیکسل مجاز نیست.

پیش‌نیازها:

- Node.js 20 یا جدیدتر
- npm
- دسترسی به پروژه Supabase نووا

راه‌اندازی:

```bash
git clone https://github.com/esi-khafan1/nova.git
cd nova
npm install
cp .env.example .env.local
npm run dev
```

سپس سایت را در `http://localhost:3000` باز کنید.

### متغیرهای محیطی

```env
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=your-publishable-key
```

کد فعلی برای سازگاری، `NEXT_PUBLIC_SUPABASE_ANON_KEY` را نیز به‌عنوان جایگزین کلید publishable می‌پذیرد.

مقادیر واقعی را فقط در `.env.local`، تنظیمات Cloudflare Workers یا ابزار امن مدیریت Secrets قرار دهید. هیچ کلید خصوصی، `service_role`، رمز عبور یا توکن دسترسی را داخل Git، README یا چت قرار ندهید.

## وابستگی‌های مورد انتظار در Supabase

کد فعلی انتظار دارد این موارد در پروژه Supabase موجود باشند:

- Supabase Auth با ورود ایمیل و رمز عبور

قبل از تغییر Schema، Migration یا Policyها ابتدا وضعیت فعلی پروژه Supabase بررسی شود. تغییرات دیتابیس بدون تأیید و بدون برنامه بازگشت انجام نشوند.

## گردش کار Git و انتشار

1. آخرین نسخه `main` را دریافت کنید.
2. برای هر قابلیت یا اصلاح، یک شاخه جدید از `main` بسازید؛ مانند:
   - `feature/...`
   - `fix/...`
   - `chore/...`
3. تغییرات فقط روی همان شاخه Push شوند.
4. Cloudflare برای شاخه، Preview Deployment می‌سازد.
5. بعد از **هر Push**، Agent باید منتظر بماند تا Deployment در Cloudflare به وضعیت نهایی `Success` یا `Failed` برسد؛ قبل از آن نباید کار را تکمیل‌شده اعلام کند.
6. پس از موفقیت Deployment، Agent باید لینک دقیق همان Preview را در پاسخ برای صاحب پروژه ارسال کند. اگر Deployment ناموفق بود، ابتدا Build Log بررسی و خطا برطرف شود.
7. Preview در دسکتاپ و موبایل بررسی و ایرادات برطرف شوند.
8. پس از موفقیت `lint` و `build`، Pull Request به `main` ساخته شود.
9. ادغام با `main` فقط بعد از تأیید صریح صاحب پروژه انجام شود.
10. `main` نسخه Production است؛ تغییر آزمایشی مستقیماً روی آن Push نشود.

استثنا: تغییر صرفاً مستنداتی مثل README، در صورت درخواست صریح صاحب پروژه، می‌تواند مستقیم روی `main` انجام شود.

## راه‌اندازی سریع یک سشن جدید با AI

برای اینکه در یک سشن جدید نیازی به توضیح دوباره پروژه نباشد، اتصال‌های زیر را آماده کنید.

### 1. GitHub

اتصال رسمی GitHub/MCP را فعال کنید و به repository زیر دسترسی خواندن و نوشتن بدهید:

```text
esi-khafan1/nova
```

دسترسی موردنیاز:

- خواندن فایل‌ها و تاریخچه Commitها
- ساخت Branch
- Push فایل و Commit
- ساخت و به‌روزرسانی Pull Request
- خواندن وضعیت Branch و PR

در ابتدای سشن از AI بخواهید ابتدا `README.md`، آخرین `main`، Branch فعال و PRهای باز را بخواند. دسترسی حذف Repository یا مدیریت تنظیمات سازمان لازم نیست.

### 2. Supabase

اتصال رسمی Supabase را فعال کنید و پروژه‌ای با نام `nova` را در اختیار سشن قرار دهید.

برای عیب‌یابی کامل، اتصال باید امکان موارد زیر را بدهد:

- مشاهده Schema، Tableها، Functionها و Policyها
- اجرای Queryهای فقط‌خواندنی برای بررسی داده
- مشاهده Auth و خطاهای مرتبط، در حدی که اتصال رسمی ارائه می‌کند
- مشاهده Logهای دیتابیس و API
- اجرای Migration فقط هنگام درخواست و پس از تأیید

از ارسال دستی رمز، access token، کلید `service_role` یا اطلاعات ورود در چت خودداری کنید.

### 3. مرورگر اشتراکی و Cloudflare

در ابتدای هر سشن، **دسترسی استفاده از مرورگر اشتراکی برای Agent باید فعال باشد**. صرفاً متصل بودن GitHub/MCP یا Supabase کافی نیست؛ Agent برای باز کردن داشبورد Cloudflare، بررسی Deployment، مشاهده Build Log و Runtime Log، مدیریت متغیرهای محیطی و تست Preview به دسترسی مرورگر نیاز دارد.

پس از فعال شدن مرورگر، Agent باید صفحه ورود Cloudflare را باز کند و با ایمیل و رمز عبور حساب مالک پروژه وارد شود. ایمیل، رمز عبور و کد تأیید باید فقط از ورودی امن مرورگر دریافت شوند و هرگز در چت، Commit یا Log قرار نگیرند. گزینه **Save email and login method on this device** روشن بماند. بعد از ورود، Worker با نام `nova`، آخرین Deployment و دامنه `nova-academy.ir` بررسی شوند.

مراحل الزامی شروع سشن:

1. دسترسی مرورگر اشتراکی را فعال کن.
2. `https://dash.cloudflare.com/login` را در مرورگر باز کن.
3. ایمیل و رمز عبور Cloudflare را فقط از ورودی امن مرورگر دریافت کن و وارد شو.
4. اگر کد تأیید درخواست شد، آن را نیز فقط از ورودی امن مرورگر دریافت کن.
5. پس از ورود، Worker با نام `nova`، آخرین Deployment، Build Log، Runtime Log و دامنه `nova-academy.ir` را بررسی کن.

موارد موردنیاز:

- مشاهده Production و Preview Deploymentها
- مشاهده Build Log و Runtime Log
- مشاهده وضعیت Variables و Secrets بدون افشای مقدار Secretها
- بررسی Domains and Routes و اتصال `nova-academy.ir`
- Redeploy در صورت نیاز

برای این پروژه، مسیر پیش‌فرض دسترسی به Cloudflare همان ورود مرورگری با ایمیل و رمز عبور است. اطلاعات ورود باید فقط از ورودی امن مرورگر دریافت شوند.

### 4. پیام پیشنهادی شروع سشن

پس از برقرار شدن اتصال‌ها، این پیام برای شروع سریع کافی است:

```text
روی پروژه Nova در repository `esi-khafan1/nova` کار کن. ابتدا README، آخرین main، Branchهای فعال و PRهای باز را بررسی کن. دسترسی مرورگر اشتراکی را فعال کن و صفحه ورود Cloudflare را باز کن؛ ایمیل، رمز عبور و کد تأیید را فقط از ورودی امن مرورگر دریافت کن. Worker با نام nova، آخرین Deployment، دامنه nova-academy.ir و Preview مربوط به Branch فعال را باز و بررسی کن. برای تغییرات کد از main یک Branch جدید بساز. بعد از هر Push منتظر تکمیل Deployment Cloudflare بمان، نتیجه را بررسی کن و لینک دقیق Preview را برای من بفرست. بدون تأیید من Merge نکن. برای دیتابیس و Auth فقط از اتصال رسمی Supabase استفاده کن. اگر باگ گزارش کردم، ابتدا Logهای Vercel و Supabase را بررسی کن و بعد کمترین اصلاح امن را انجام بده.
```

اگر قرار است کار قبلی ادامه پیدا کند، نام Branch یا لینک PR را نیز در همان پیام بنویسید.

## قواعد ایمنی برای Agent

- قبل از ویرایش، وضعیت Branch و آخرین Commit بررسی شود.
- تغییرات محلی یا کار ناتمام دیگران بدون اجازه حذف یا بازنویسی نشود.
- برای هر کار کدنویسی از Branch مجزا استفاده شود.
- هیچ Secret یا اطلاعات شخصی در خروجی، Log، Commit یا PR قرار نگیرد.
- تغییرات دیتابیس ابتدا بررسی و سپس با Migration قابل بازگشت انجام شوند.
- برای رفع باگ، ابتدا شواهد از Logها جمع‌آوری و سپس کوچک‌ترین اصلاح ممکن اعمال شود.
- بعد از هر Push، تکمیل Deployment Cloudflare بررسی و لینک دقیق Preview گزارش شود.
- قبل از Merge، Preview و Build نهایی بررسی شوند.
- Merge و انتشار عمومی فقط با تأیید صاحب پروژه انجام شود.

- محافظت در برابر ترتیب CSS در خروجی واقعی Next: چیدمان مسیر تحصیلی گوشی همیشه ۲×۲ باشد؛ رنگ کارت‌های شبکه‌های اجتماعی در حالت پیش‌فرض همان سفید تأییدشده بماند، نه گرادیان نارنجی استایل پایه. تست باید computed style خروجی deploy را هم بررسی کند، نه فقط وجود قواعد در فایل CSS.

### تم تأییدشدهٔ مجله — آرشیو و مقاله

- فقط مسیرهای `/mag` و `/mag/[id]`: تم آبی یخی، سفید و نارنجی، با **همان کامپوننت LandingHeader لندینگ** و لوگوی `/nova/mark.svg`. تغییر کامپوننت Logo سراسری، خبر، پادکست یا لندینگ برای این کار مجاز نیست.
- آرشیو گوشی: دو ستون کارت در تمام عرض‌های ۳۲۰ تا ۷۰۰؛ همهٔ مقاله‌ها حفظ شوند (محدودیت دو کارت فقط برای پیش‌نمایش لندینگ بود). توضیح کوتاه کارت مخفی باشد؛ عنوان، عکس، دسته‌بندی، تاریخ و لینک حفظ شوند. تاریخ راست و «بخوان» چپ همان ردیف؛ متن در ستون خودش بشکند، نه روی ستون دیگر. لوگوی تکراری فوتر در گوشی نمایش داده نشود.
- مقاله گوشی: **متن کامل، خلاصه مقاله، نویسنده، تاریخ، تصاویر، نقل‌قول‌ها، فهرست‌ها و لینک‌ها** حفظ شوند. اندازه متن مقاله حداقل ۱۶ و اطلاعات جانبی حداقل ۱۴ پیکسل؛ بدون اسکرول افقی یا برش متن. لینک بازگشت به مجله و دسترسی خانه/حساب کاربری حذف نشوند.
- CSS فقط زیر `.magazine-theme` و از layout مجله بارگذاری شود. کوئری‌ها، ترتیب انتشار، داده و محتوای مقاله‌ها، metadata و renderer مشترک RichContent دست‌نخورده بمانند. منو، سبد خرید، حالت خالی و مقاله‌های طولانی در گوشی و دسکتاپ بررسی شوند.
