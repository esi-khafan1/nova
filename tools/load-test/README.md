# تست بار دستی نوا

این ابزار **فقط با `workflow_dispatch`** اجرا می‌شود. هیچ trigger مربوط به push، PR یا زمان‌بندی ندارد و هیچ تغییر دیتابیس یا فرم ثبت پاسخ انجام نمی‌دهد. به فایل‌های برنامه و روش استقرار نوا وابسته نیست.

## اجرای دستی در GitHub

1. در مخزن `esi-khafan1/nova` وارد **Actions → Nova · Manual load test** شو.
2. **Run workflow** را بزن؛ branch را روی `main` بگذار.
3. `max_users` را مثلاً `10` یا `100` انتخاب کن. این سقف است؛ بار به‌تدریج افزایش پیدا می‌کند.
4. `target` را انتخاب کن. برای سایت اصلی باید `confirm_production` را خودت تیک بزنی. پیش‌نمایش ممکن است نسخهٔ متفاوتی از سایت اصلی باشد؛ پیش از تست بررسی‌اش کن.
5. برای شروع، سناریوی `public` و مقدارهای پیش‌فرض را نگه دار.
6. بعد از اجرا، خلاصهٔ نتیجه داخل همان Run نمایش داده می‌شود. در **Artifacts** فایل `nova-load-test-...` را دانلود و ZIP را استخراج کن. `report.html` را در مرورگر باز کن؛ اینترنت یا افزونه لازم ندارد.

### ورودی‌ها

| ورودی | پیش‌فرض | کاربرد |
|---|---|---|
| `target` | production | فقط دامنهٔ اصلی یا آدرس preview شناخته‌شده؛ آدرس دلخواه پذیرفته نمی‌شود |
| `max_users` | 10 | سقف کاربر مجازی هم‌زمان، از ۱ تا ۵۰۰ |
| `step_seconds` | 60 | مدت هر پله، ۶۰ تا ۱۸۰ ثانیه؛ برای نتیجهٔ مطمئن‌تر ۹۰ یا ۱۲۰ مناسب‌تر است |
| `p95_limit_ms` | 2000 | حد p95، از ۱۰۰ تا ۱۰۰۰۰ میلی‌ثانیه |
| `error_limit_percent` | 1 | حد درصد خطا، از ۰ تا ۱۰ |
| `scenario` | public | صفحات عمومی یا دریافت خواندنی فهرست آزمون دانش‌آموز |
| `confirm_production` | false | تأیید آگاهانهٔ تست روی سایت اصلی و مصرف سرویس/هزینهٔ احتمالی |

## افزایش بار و توقف

پله‌ها `1 → 5 → 10 → 25 → 50 → 75 → 100 → 150 → 200 → 300 → 400 → 500` هستند؛ فقط پله‌های تا سقف انتخاب‌شده اجرا می‌شوند و خودِ سقف هم اضافه می‌شود؛ مثلاً سقف ۳۵ برابر است با `1,5,10,25,35`.

- هر پله یک اجرای مستقل k6 با تعداد VU ثابت است؛ پله‌ها هم‌پوشانی ندارند و همهٔ کاربران مجازی در پایان هر پله متوقف می‌شوند.
- بین درخواست‌های هر کاربر ۱ تا ۳ ثانیه مکث تصادفی وجود دارد؛ ۱۰۰ کاربر به معنی ۱۰۰ درخواست در ثانیه نیست.
- ۱۰ ثانیهٔ اول هر پله از آمار کنار گذاشته می‌شود؛ نتیجه، معیار cold-start نیست.
- زمان پاسخ p95 یا درصد خطا اگر در **دو بازهٔ متوالی ۱۵ثانیه‌ای** از حد عبور کند، اجرای جاری متوقف می‌شود و پلهٔ بالاتری اجرا نمی‌شود. هر بازه حداقل ۱۰ درخواست لازم دارد؛ بازهٔ ناکافی توالی را قطع می‌کند.
- در پایان هر پله هم کل داده‌های اندازه‌گیری‌شده بررسی می‌شود؛ با حداقل ۲۰ درخواست، عبور از هر حد جلوی پلهٔ بعدی را می‌گیرد. بنابراین یک پله با الگوی پراکندهٔ کندی هم ممکن است در پایان متوقف شود، حتی اگر محافظ دوبازه‌ای فعال نشده باشد.
- نمونهٔ کمتر از ۲۰ درخواست یا خطای ابزار هم باعث توقف می‌شود؛ چنین نتیجه‌ای نباید ظرفیت سرور تفسیر شود.
- درخواست بیشتر از ۱۰ ثانیه منتظر نمی‌ماند. سقف کلی هر Job برابر ۴۵ دقیقه است. Workflowها در همهٔ branchها یک گروه concurrency دارند؛ دو تست GitHub هم‌زمان اجرا نمی‌شوند.
- توقف محافظ **نتیجهٔ معتبر تست** است، نه خطای CI؛ Run می‌تواند سبز باشد ولی خلاصه بگوید بار متوقف شده. اشکال اجرای ابزار Run را ناموفق می‌کند. حتماً خلاصه را بخوان.

بهتر است با اولین علامت تک‌درخواستی متوقف نشویم، چون ممکن است نوسان شبکه باشد. اما ادامه‌دادن بعد از کندی تأییدشده هم لازم نیست. بعد از توقف، ابتدا اجازه بده سایت آرام شود؛ برای دقت بیشتر، بعداً بین آخرین پلهٔ سالم و اولین پلهٔ ناموفق تست کوتاه‌تری انجام بده. ابزار خودش تست دوم یا بار بیشتر راه نمی‌اندازد.

## سناریوها و محدودیت مهم

### `public` — آماده، بدون secret

درخواست GET به خانه، اخبار، پادکست و دربارهٔ ما. HTTP 200 با محتوای HTML لازم است؛ redirect، خطای HTTP و challenge مشخص Cloudflare خطا حساب می‌شوند. کش CDN روشن و رفتار عادی سایت حفظ می‌شود؛ cache-busting اضافه نمی‌شود.

**این نتیجه ظرفیت شرکت در آزمون، ذخیرهٔ پاسخ، ورود هم‌زمان یا کارنامه را ثابت نمی‌کند.** این یک تست HTTP تک‌منطقه‌ای است، نه مرورگر واقعی؛ JS، تصویر، PDF، لود فونت و رندر صفحه را اندازه نمی‌گیرد. p95 از زمان HTTP درخواست به دست می‌آید، نه زمان نمایش کامل صفحه.

### `student` — اختیاری، نیازمند نشست تستی

فقط GET صفحهٔ `/dashboard/student/exams` انجام می‌دهد و وجود عنوان آزمون‌ها در HTML را کنترل می‌کند. redirect به ورود یا نشست منقضی خطاست؛ ابزار برای سبزکردن نتیجه به صفحات عمومی برنمی‌گردد.

در **Settings → Secrets and variables → Actions** یک **repository secret** با نام `NOVA_LOAD_TEST_STUDENT_COOKIES` اضافه کن؛ مقدارش یک آرایهٔ JSON از رشته‌های کامل هدر Cookie نشست‌های **حساب‌های تستی دانش‌آموز فعال** است. نمونهٔ ساختار زیر واقعی نیست:

```json
["sb-PROJECT-auth-token=TEST_SESSION_COOKIE", "sb-PROJECT-auth-token=ANOTHER_TEST_SESSION_COOKIE"]
```

اگر کوکی چندبخشی باشد، همهٔ بخش‌ها را در همان رشته با `; ` جدا کن. از حساب واقعی دانش‌آموز، مدیر یا service-role key استفاده نکن. Cookie یک credential حساس است؛ آن را در کد، ورودی Workflow، Issue، چت یا artifact نگذار. هر وقت نشست منقضی شد secret را جایگزین کن؛ پس از تست نشست‌ها را باطل کن.

نشست‌ها به‌ترتیب میان VUها توزیع می‌شوند؛ مثلاً ۱ نشست با ۱۰۰ VU یعنی ۱۰۰ کاربر مجازی با **یک هویت مشترک**، نه ۱۰۰ دانش‌آموز متفاوت. تعداد نشست‌ها در گزارش ثبت می‌شود، خودِ کوکی‌ها نه. برای تست چندکاربرهٔ واقعی، نشست‌های تستی مستقل لازم است. ورود به حساب جزو زمان تست نیست. RLS و احراز هویت عادی سایت دور زده نمی‌شوند. صفحهٔ GET ممکن است تمدید طبیعی session انجام دهد؛ تست نوشتنی آزمون نیست.

## خروجی و تفسیر

- `report.html`: نمودار p95 و درصد خطا در برابر تعداد کاربران + خطوط حد توقف + جدول قابل مشاهده و تفکیک مسیرها و نوع پاسخ‌ها (مثلاً 429، 403، timeout)؛ مستقل از CDN و بدون JS خارجی.
- `summary.json`: داده و نتیجهٔ قابل پردازش، زمان UTC و حدود انتخاب‌شده.
- `stages.csv`: آمار هر پله.
- `windows.csv`: بازه‌های ارزیابی محافظ.
- `summary.md`: خلاصهٔ GitHub و جدول.

اگر تا ۱۰۰ نفر سالم بود، نتیجه فقط «تا ۱۰۰ کاربر در این سناریو و این زمان حد رد نشد» است؛ نه «ظرفیت سایت دقیقاً ۱۰۰ نفر است». اگر پلهٔ ۷۵ سالم و ۱۰۰ ناموفق شد، مرز مشاهده‌شده بین این دو است، نه یک عدد قطعی. خطا ممکن است از WAF، نشست نامعتبر، rate limit، دیتابیس یا شبکه باشد. برای علت، داشبورد Cloudflare و Supabase را در بازهٔ UTC گزارش مقایسه کن.

آمار ۱۰کاربره فقط smoke test ابزار است؛ برای ادعای ظرفیت کافی نیست. اجراهای بزرگ‌تر را در ساعات خلوت و ترجیحاً محیط آزمایشی با پلن، داده و تنظیمات مشابه تولید انجام بده. حتی GET ممکن است لاگ و مصرف سهمیه/هزینه بسازد. یک GitHub Runner هم ممکن است خودش گلوگاه شود؛ نتیجهٔ بزرگ را بدون کنترل این موضوع قطعی فرض نکن.

## اجرای محلی

k6 نسخهٔ `1.0.0` و Python 3.11+ لازم است. وابستگی pip یا npm جدیدی لازم نیست:

```sh
python3 tools/load-test/test_runner.py
python3 tools/load-test/run.py --target production --confirm-production --max-users 10 --step-seconds 60 --output /tmp/nova-load-results
```

برای سناریوی student، مقدار `NOVA_STUDENT_COOKIES` را امن در محیط پردازش تنظیم کن؛ روی خط فرمان ننویس. برای هر اجرا پوشهٔ خروجی جدید بده. نتیجه‌ها و secretها را commit نکن.

## ایمنی و نگهداری

- تنها متد شبکهٔ سناریو GET است؛ هیچ POST، PATCH، ارسال پاسخ، ساخت کاربر یا migration وجود ندارد.
- هیچ response body، هدر Cookie یا raw metric log در artifact آپلود نمی‌شود. دادهٔ خام موقت پس از هر پله حذف می‌شود.
- Actions به commit مشخص pin شده‌اند؛ k6 هم نسخه و SHA-256 ثابت دارد.
- ورودی‌ها از environment و argparse عبور می‌کنند؛ داخل shell/code تزریق نمی‌شوند. مقصدها allowlist ثابت دارند.
- `GITHUB_TOKEN` فقط دسترسی read دارد؛ Checkout credential را در git باقی نمی‌گذارد.
- retention خروجی‌ها ۱۴ روز است؛ قطع اجباری runner یا timeout کلی ممکن است اجازهٔ آپلود گزارش نهایی ندهد. برای توقف عادی از Cancel workflow استفاده کن، اما برای حفظ گزارش کامل به محافظ خودکار تکیه کن.
