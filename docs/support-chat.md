# Website support and enrollment follow-up

## Behavior and permissions

A lazy-loaded, fixed bottom-right support widget is mounted in the root layout on every page. Guests can send text without signing up or supplying a name/contact number. Signed-in conversations show the existing profile name only in the support inbox. Replies exposed to visitors contain only message ID, body, timestamp and the generic sender kind `support`; staff names/IDs never go to visitors. Text is rendered as escaped React text, never HTML. There are no attachments or Presence/typing indicators.

`/dashboard/support_agent` is role-guarded and has shared unanswered/answered inbox tabs, pagination and conversation history. Each visitor message marks its conversation unanswered; a staff reply marks it answered. All staff share these queues. Ordinary admins and superadmins can assign/remove `support_agent` through the existing user-role form. Protected superadmin accounts, admin promotions and content-manager role boundaries stay intact. Support agents gain no educational, receipt-approval or role-management permissions.

Guests use a cryptographically random 256-bit HttpOnly/SameSite cookie, with only its SHA-256 hash in the private database. It is never returned in JSON, URLs or Realtime events. Cookie deletion/expiry means anonymous history cannot be recovered on another device; signing in attaches that conversation to that account, but the cookie remains necessary to locate it. Account-owned conversations require the same authenticated UID and never become guest-readable after account deletion (ownership tombstone retained). Logout/account changes clear the mounted UI; mismatched sessions clear the capability cookie and start a new conversation. All SQL functions use empty search paths and explicit role/ownership checks. Direct table access is revoked and RLS is enabled. API staff access additionally requires fresh Auth and matching own-profile identity/role; an invalid/revoked Auth user uses a separate public-only client rather than stale SSR JWT identity. POST requires same-origin and bounded JSON input.

Limits: messages are at most 2,000 characters; guest/visitor messages have a two-second spacing and 60/hour per conversation; new conversations are capped at 60/minute project-wide. These are abuse controls, not a claim of comprehensive distributed bot/DDoS protection. Production gateway/IP rate limits or a challenge may still be required under abuse. No anonymous Auth accounts, service-role secrets or new credentials are used.

## Actual Realtime and quota handling

Message inserts trigger Supabase `realtime.send` Broadcast invalidations on an opaque per-conversation topic and an opaque staff-inbox topic. These public capability topics carry **only `{changed:true}`**, never chat text, names, visitor secrets or staff IDs. Visitors cannot use knowledge of a topic to read messages: the HTTP/SQL ownership checks remain mandatory. The staff inbox topic is issued only by a staff-guarded RPC. Public topic knowledge can reveal activity/invalidation, so it is not treated as authorization for confidential data. No chat tables are exposed through Postgres Changes or realtime publications.

The browser's existing singleton Supabase client multiplexes active channels on one socket per browser context. A closed widget has no subscription or background fetch. An empty, never-messaged chat also needs no socket. An open visitor conversation uses one channel; the staff inbox plus selected conversation normally uses two channels on one socket. Visibility-hidden tabs remove subscriptions, and showing a tab refetches history and reconnects. Cleanup explicitly disconnects the socket when there are no remaining channels: the installed SDK otherwise defaults to a deferred empty-channel disconnect. Join jitter and bounded transport reconnect backoff reduce reconnect bursts. Notifications coalesce for 180ms, and HTTP reads are incremental in complete 200-message batches. There is no three-second polling loop.

A successful subscription and every reconnect trigger a fresh read to recover missed messages. An exceptional 60-second reconciliation read while connected covers lost invalidations; failed/unavailable Realtime uses a visible reconnecting state and 30-second HTTP reconciliation. These are fallbacks, not represented as a live socket. Notification exceptions never roll back a stored message. SQL throttling queries have dedicated indexes. No plan, spending cap, Realtime quota or SMTP setting was changed.

Official limits checked 2026-10-23:
- https://supabase.com/docs/guides/realtime/limits — documented defaults include Free 200 concurrent connections / 100 messages per second, Pro 500 / 500, plus join/channel limits. Per-project overrides and other plans differ.
- https://supabase.com/docs/guides/platform/manage-your-usage/realtime-messages — documented monthly quotas: Free 2 million, Pro 5 million. Broadcast accounting includes the send **and each subscriber delivery**; a tiny invalidation is not free or a way around billing. Each chat message generates two notifications, with fan-out increasing usage as more staff view the inbox.
